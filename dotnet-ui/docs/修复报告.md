# Pathwinder 修复报告

- 环境：Windows，Pathwinder（Hookshot 注入式路径重定向）
- 汇总：微信笔记打不开（v1 / v2，2026-10-30 / 10-31）；QQ 群文件打不开（v1，2026-11-06）
- 共同原则：**重定向对进程必须构成一个自洽的“幻觉”**。文件访问、进程创建、shell 交棒、路径规范化与卷查询任一环节把真实路径/真实卷泄漏出去，调用方就会因为“看到的位置和自己记录的不一致”而静默中止。因此所有修复都只判断“该路径/该句柄是否命中重定向规则”，不包含任何针对具体应用的硬编码分支（无进程名、无固定目录名）。

---

## 一、微信笔记/收藏卡片无法打开

### v1：CreateProcessW 三层路径泄漏（2026-10-30，已实测通过）

**现象**：把微信数据目录从 C: 重定向到 D: 后，微信本体正常，点击笔记/收藏卡片无任何反应。

规则：

| 规则 | 源目录 (C:) | 目标目录 (D:) |
|---|---|---|
| WechatData | `C:\Users\39313\AppData\Roaming\Tencent\xwechat` | `D:\APP\PathwinderManager\data\微信\39313\AppData\Roaming\Tencent\xwechat` |
| WechatFiles | `C:\Users\39313\xwechat_files` | `D:\APP\PathwinderManager\data\微信\39313\xwechat_files` |

**根因**：笔记由内嵌 Chromium 插件 `WeChatAppEx.exe`（RadiumWMPF）渲染，其可执行文件位于被重定向的目录下。文件钩子（NtCreateFile / NtOpenFile 等）只覆盖进程内的文件访问；**创建子进程是内核行为**，内核自行解析映像路径与工作目录，不经过任何文件钩子，于是三层 C: 路径被带进子进程：

| 层 | 泄漏内容 | 后果 |
|---|---|---|
| ① 进程映像 | `lpApplicationName` / 命令行首 token 指向 C: 的 WeChatAppEx.exe | 内核找不到映像，进程创建失败 |
| ② 工作目录 | `lpCurrentDirectory` 指向 C: 下已不存在的运行时目录 | CreateProcess 整体失败 |
| ③ 命令行参数 | `--flue-runtime-dir=`、`--wmpf_root_dir=` 等仍是 C: | 进程能启动但立刻退出 |

**修复**：钩 `kernelbase!CreateProcessW`（不钩 `NtCreateUserProcess`：该调用期间调用方持有 loader lock，钩内做规则查询/文件探测/日志会死锁）。钩内做三件事：
1. 映像路径命中规则且目标文件真实存在才改写（进程创建没有重试机会）；
2. 命令行全路径扫描（`"` / `=` / `,` / 空格 / 行首之后的 `X:\...` 段），无条件执行，避免 `lpApplicationName` 非空时漏改 crashpad 等参数；
3. 工作目录命中规则且目标目录存在时改写。

**验证**：修复前 WeChatAppEx 存活数 0，修复后 10；日志出现 `Redirecting command line path from "C:\...\xwechat\crashinfo" to "D:\...\xwechat\crashinfo"`。

**排除的干扰项**：`0xc00000ba`（STATUS_FILE_IS_A_DIRECTORY，Chromium 的探测重试）、`0xc0000034`（首次运行缓存未命中）均为正常现象。

### v2：环境变量块路径泄漏（2026-10-31，已实测通过）

**现象**：微信把 WeChatAppEx 从 25799 自动升级到 25819 后，笔记再次打不开。

**根因**：v1 重写的三层全部生效，但新版本改为从**环境变量**推导数据目录（`%APPDATA%` / `%LOCALAPPDATA%` / `%USERPROFILE%` / `%TEMP%` / `%PUBLIC%` 等）。子进程初始化发生在 Pathwinder 注入之前，这些 C: 路径不经过任何文件钩子。

**修复**：在 `CreateProcessW` 钩子里增加第四层——重写传递给子进程的环境变量块：遍历 `NAME=VALUE\0` 对，值为 `X:\...` 形态且命中规则的改写为目标路径，全部改写完成后用重建的块替代 `lpEnvironment`。

**验证**：日志出现 `Redirecting environment variable "APPDATA" from "C:\Users\39313\AppData\Roaming" to "D:\...\data\微信\39313\AppData\Roaming"`，`LOCALAPPDATA`/`USERPROFILE`/`TEMP`/`TMP`/`PUBLIC`/`OneDrive` 全部重定向；删除 NTFS Junction 后笔记仍可正常打开。

**被否决的方案**：手动两阶段远程注入（Hookshot 在 Chromium 早期进程中初始化崩溃）；NTFS Junction（透明但不满足“代码层解决”的要求）。

## 二、QQ 群文件无法打开

### v1：路径规范化与卷查询泄漏真实位置（2026-11-06，日志已确认）

**现象**：把 `C:\Users` 重定向到 `D:\APP\PathwinderManager\data\QQ` 后，QQ 群文件 `Desktop.7z` 的“打开”与“打开所在文件夹”都无反应；同一条目的“另存为”正常。无重定向时一切正常。

**取证（修复前，09:04:05 点击的全部动作）**：

| 顺序 | 调用 | 结果 |
|---|---|---|
| 1 | `NtQueryAttributesFile(C:\Users\39313\Downloads\Desktop.7z)` | 重定向到 D:，`0x0` |
| 2 | `NtCreateFile(Desktop.7z, FILE_READ_ATTRIBUTES\|SYNCHRONIZE, ShareAccess=0, FILE_OPEN_FOR_BACKUP_INTENT)` | `0x0` |
| 3 | `NtCreateFile(\??\MountPointManager)` | 查卷（非盘符路径，不参与重定向） |
| 4 | `NtClose` | — |
| 5 | 之后 | **无任何** `ShellExecuteW/ExW`、`SHOpenFolderAndSelectItems`、`SHParseDisplayName`、`ILCreateFromPathW`、`CreateProcessW` |

第 2、3、4 步正是 Electron/Chromium 路径规范化（`fs.realpath`）的固定动作：开句柄 → `GetFinalPathNameByHandleW` 解析卷路径 → 关句柄。

**根因**：该系统调用把文件真实落盘位置 `\??\D:\APP\PathwinderManager\data\QQ\39313\Downloads\Desktop.7z` 报给了 QQ，且该句柄上原函数直接返回失败；QQ 拿它和自己记录的 `C:\Users\...` 对比不一致，于是静默中止，根本没有走到 shell 交棒。`\??\MountPointManager` 这次查卷不受重定向影响，进一步把“文件在 D: 卷”的事实透了出去。

**修复**（两处，均按“命中规则才生效”）：

| 钩子 | 行为 |
|---|---|
| `GetFinalPathNameByHandleW` | 句柄若来自一次被重定向的打开（OpenHandleStore 中关联路径 ≠ 实际打开路径），返回**关联的源路径**（`\\?\C:\Users\...`）；支持 `VOLUME_NAME_DOS` 与 `VOLUME_NAME_NONE` 两种形态；`VOLUME_NAME_GUID`/`VOLUME_NAME_NT` 无法由源路径推导，原样放行；缓冲区不足时按 API 约定返回所需大小 |
| `GetVolumePathNameW` | 路径命中规则时返回**源盘符根**（`C:\`），不再泄漏真实卷 |

原有的 shell 钩子（`SHOpenFolderAndSelectItems` / `SHCreateItemFromParsingName` / `ILCreateFromPathW` / `ShellExecuteExW` 等）继续把 C: 路径换算成真实 D: 目标，因此 Explorer 打开的是文件真正所在的文件夹。

**验证（修复后，QQ 主进程日志，四次点击 10:33:51 / 10:33:56 / 10:33:59 / 10:34:04 均相同）**：

```
GetFinalPathNameByHandleW: Handle 6748 resolves to
  "\??\D:\APP\PathwinderManager\data\QQ\39313\Downloads\Desktop.7z"
  but is reported as "\\?\C:\Users\39313\Downloads\Desktop.7z"
↓ 同一秒
SHOpenFolderAndSelectItems: Entry with folder=<present>, cidl=1, flags=0x00000000
ILCreateFromPathW: Entry with path "D:\APP\PathwinderManager\data\QQ\39313\Downloads"
SHOpenFolderAndSelectItems: Redirecting shell folder from "C:\Users\39313\Downloads"
                          to "D:\APP\PathwinderManager\data\QQ\39313\Downloads"
```

修复前同一动作只有 `CreateFile → \??\MountPointManager → CloseHandle`，没有任何 shell 调用；修复后出现完整的 shell 交棒链，用户实测“打开所在文件夹”正常。

**部署物**：`payload\Pathwinder.HookModule.64.dll`（326,144 字节）/ `Pathwinder.HookModule.32.dll`（276,992 字节），通过 NTFS 硬链接同步到全部 18 个 runtime 目录；钩子总数 22（新增 2 个）。诊断日志已移除，`LogLevel` 恢复为 3。

## 三、代码通用性审查结论

三处修复都不含应用相关的判断，全部以“路径/句柄是否命中重定向规则”为唯一条件：

- `LookupRedirectedTargetPath()`：统一的规则查询入口，只接受绝对盘符路径，返回去掉命名空间前缀后的目标路径；
- `RewriteEmbeddedPaths()`：对任意参数字符串做全路径扫描，与调用方是哪个程序无关；
- 新增的两个卷/路径钩子：只比较 OpenHandleStore 中的“关联路径”与“实际打开路径”是否不同，或路径是否命中规则，不依赖进程名、文件类型或固定目录。

因此同一套代码可覆盖同类故障：任何对重定向文件做路径规范化、卷判断、shell 交棒或子进程创建的应用程序（Electron/Chromium 系、调用 `ShellExecuteEx` 的下载器、以及依赖 `lpCurrentDirectory`/环境变量定位资源的启动器）都会被同样修正。

## 四、构建与部署注意事项

- 构建工具：VS2022 BuildTools（`D:\APP\vs2022\BuildTools`），Release x64 / Win32。
- 必须带环境变量 `$env:CL='/utf-8 /wd4828 /wd4819'`：Infra 的 `Configuration.cpp` 混入 GBK 字节会触发 C4819/C4828，而 `NativeBuild.props` 硬编码 `TreatWarningAsError=true`，`/p:` 覆盖不掉，只能用 `/wd` 屏蔽。
- `payload\` 与 `runtime\<hash>\` 下的 DLL 通过 **NTFS 硬链接**关联，写任一处即全局生效；但 DLL 被正在运行的程序（如已注入的第三方应用）映射时无法覆盖，需先改名占用中的旧文件、再复制新文件、然后对每个 runtime 副本重建硬链接。
- 不要用 PathwinderManager 的部署功能（它会把 `LogLevel` 重置为 0 并可能覆盖 DLL）；直接替换 `payload` 目录的 DLL 即可。
- 应用运行时日志文件被独占打开（共享模式为 0），分析前需先退出应用，或用支持 `FileShare::ReadWrite` 的方式复制。
