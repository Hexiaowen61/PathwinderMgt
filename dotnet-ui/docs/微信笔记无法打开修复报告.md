# 微信笔记/收藏卡片无法打开 — 诊断与修复报告

- 日期：2026-10-30
- 环境：Windows，微信（Weixin）4.1.15.56，Pathwinder 路径重定向
- 状态：**已修复并实测通过**（笔记可正常打开）

---

## 1. 问题现象

启用 Pathwinder 把微信数据目录从 C: 重定向到 D: 后：

- 微信本体（Weixin.exe）启动正常，聊天等功能正常；
- **点击笔记/收藏卡片时无任何反应**，窗口打不开。

Pathwinder 规则（Simple 模式，2 条）：

| 规则 | 源目录 (C:) | 目标目录 (D:) |
|---|---|---|
| WechatData | `C:\Users\39313\AppData\Roaming\Tencent\xwechat` | `D:\APP\PathwinderManager\data\微信\39313\AppData\Roaming\Tencent\xwechat` |
| WechatFiles | `C:\Users\39313\xwechat_files` | `D:\APP\PathwinderManager\data\微信\39313\xwechat_files` |

## 2. 根本原因

笔记/收藏卡片由微信的内嵌浏览器插件 **WeChatAppEx.exe**（RadiumWMPF，基于 Chromium）渲染。它位于被重定向的 `xwechat\xplugin\plugins\RadiumWMPF\` 目录下。

Pathwinder 原有的文件钩子（NtCreateFile / NtOpenFile 等）只能拦截**进程内的文件访问**，但**创建子进程**是内核行为：

> 内核在 `CreateProcess` 内部自行解析进程映像路径和工作目录，完全不经过任何文件钩子。

因此微信主进程拉起 WeChatAppEx 时，携带的是**原始 C: 路径**，而 C: 上这些文件已不存在（数据已迁到 D:），导致三层故障：

| 层 | 内容 | 后果 |
|---|---|---|
| ① 进程映像 | `lpApplicationName` / 命令行首个 token 指向 C: 的 WeChatAppEx.exe | 内核找不到映像，进程根本创建不出来 |
| ② 工作目录 | `lpCurrentDirectory` = `C:\...\RadiumWMPF\25799\extracted\runtime`（不存在） | 即使映像有效，整个 CreateProcess 调用也会失败 |
| ③ 命令行参数 | `--flue-runtime-dir=`、`--wechat-files-path=`、`--wmpf_root_dir=`、`--wmpf-drm-plugin-path=` 等仍是 C: | 进程能启动，但立刻因找不到运行时目录而退出 |

日志证据：修复前 WeChatAppEx 进程存活数为 **0**；修复后同一操作存活 **10 个**。

## 3. 排查过程（关键决策）

1. **首诊方向错误**：最初怀疑要钩 `NtCreateUserProcess`（最底层的进程创建系统调用）。深入后发现该调用期间调用方持有 loader lock 等内部锁，钩子里做任何常规工作（规则查询、文件探测、日志）都可能死锁 → **放弃**。
2. **改钩 `kernelbase!CreateProcessW`**：这是 Win32 层入口，不在锁内，可以安全地查询重定向规则、检查文件存在性、写日志。微信所有子进程都经由此 API 创建。
3. **开 `LogLevel = 5` 诊断日志**逐行追踪一次完整微信会话，定位到上述三层 C: 路径泄漏。
4. 渲染进程日志确认：笔记内容文件（PDF、HTM、`note.json`）、XEditor 模块（`xeditor_module.node`、`xeditor_app.dll`）经重定向后全部读取成功。
5. **排除两个干扰项**：
   - `NTSTATUS 0xc00000ba` = `STATUS_FILE_IS_A_DIRECTORY`：Chromium 用 `FILE_NON_DIRECTORY_FILE` 标志试探路径，失败后自动换方式重试，属正常行为；
   - `NTSTATUS 0xc0000034`（XEditor 缓存未命中）：首次运行缓存为空，正常。
6. **二次 review 又抓到一个漏网 bug**：当 `lpApplicationName` 非空时，初版修复只重定向映像路径、跳过了命令行重写，导致 crashpad 的 `--database=C:\...\crashinfo` 漏改（崩溃转储会写不进 C:）。已修复为命令行重写**无条件执行**。

## 4. 修复内容

只改动 3 个文件（其余调试期产物——补丁、CI、远程构建脚本——均已删除）：

| 文件 | 改动 |
|---|---|
| `Source/Hooks.cpp` | 新增 `CreateProcessW` 钩子实现（约 +248 行） |
| `Include/Pathwinder/Internal/Hooks.h` | 声明该钩子（+21 行） |
| `Source/HookModuleMain.cpp` | 注册该钩子（+1 行） |

钩子逻辑（`DynamicHook_CreateProcessW::Hook`）：

1. **映像路径**：`lpApplicationName` 命中规则时重定向到 D:；但先检查目标文件**真实存在**才改写——进程创建没有重试机会，改写成不存在的路径会把本来能启动的进程搞挂。
2. **命令行全路径扫描**（无论 `lpApplicationName` 是否提供都执行）：扫描 `"`/`=`/空格/行首之后的 `X:\...` 形态路径段，逐段查询规则并改写为目标路径；调用方缓冲区不被修改，替换串由钩子持有。
3. **工作目录**：`lpCurrentDirectory` 命中规则且目标目录存在（`GetFileAttributesW`，不排除目录）时改写。
4. 全程 Info 级日志记录入参与改写结果，便于事后审计。

部署物：`payload\Pathwinder.HookModule.64.dll`（313,856 字节），18 个 runtime 目录副本同步一致。

## 5. 验证

- **哈希一致**：部署 DLL 与编译输出 SHA256 完全相同（`AC6384AE…`）。
- **行为签名**：实测会话日志出现只有新代码才能产生的记录——
  `CreateProcessW: Redirecting command line path from "C:\...\xwechat\crashinfo" to "D:\...\xwechat\crashinfo"`。
- **用户实测**：笔记/收藏卡片可正常打开。

## 6. 收尾状态

- `Pathwinder.ini` 已恢复原样（移除诊断用 `LogLevel = 5`）；
- 桌面 11 个诊断日志（45.3 MB）已删除；
- 官方 DLL 备份已删除（如需回滚，从 git 还原 3 个源文件重新编译即可）。

## 7. 复现编译注意事项

- 构建工具：VS2022 BuildTools（`D:\APP\vs2022\BuildTools`），Release x64。
- 必须带环境变量 `$env:CL='/utf-8 /wd4828 /wd4819'`：Infra 的 `Configuration.cpp` 混入 GBK 字节会触发 C4819/C4828，且 `NativeBuild.props` 硬编码 `TreatWarningAsError=true`，`/p:` 覆盖不掉，只能用 `/wd` 屏蔽。
- 微信运行时其日志文件被占用，分析前需先复制到临时目录。

# v2：WeChatAppEx 25819 环境变量路径泄漏 — 环境变量块重写

- 日期：2026-10-31
- 环境：微信 4.1.15.56，WeChatAppEx（RadiumWMPF）版本 **25819**
- 状态：**已修复并实测通过**（笔记可正常打开，无需 NTFS Junction）
- 前置方案：v1（commit `a2206c1`）的 CreateProcessW 钩子已部署

## 1. 问题复现

v1 修复后，WeChatAppEx **25799** 可正常打开笔记。微信自动更新 WeChatAppEx 到 **25819** 后，笔记再次无法打开——点击收藏/笔记卡片无任何反应。

v1 的 CreateProcessW 钩子已正确重写了映像路径、命令行参数和工作目录，WeChatAppEx 进程能启动，但随即因找不到数据目录而退出。

## 2. 根因：第四层 C: 路径泄漏——环境变量

开 `LogLevel = 5` 追踪发现：v1 重写的三层（映像、命令行、工作目录）全部生效，但 WeChatAppEx 25819 不再仅从命令行获取数据目录，而是新增从**环境变量**推导路径：

| 环境变量 | 原始值 | 用途 |
|---|---|---|
| `%APPDATA%` | `C:\Users\39313\AppData\Roaming` | 配置、插件数据 |
| `%LOCALAPPDATA%` | `C:\Users\39313\AppData\Local` | 缓存、临时数据 |
| `%USERPROFILE%` | `C:\Users\39313` | 用户根目录（`xwechat_files` 等） |
| `%TEMP%` / `%TMP%` | `C:\Users\39313\AppData\Local\Temp` | 临时文件 |
| `%PUBLIC%` / `%OneDrive%` 等 | C: 路径 | 其他系统目录 |

WeChatAppEx（Chromium 内核）启动后调用 `SHGetKnownFolderPath` 等 API，从注册表/环境变量解析 `FOLDERID_RoamingAppData` 等，得到的仍是 C: 路径，然后**直接打开这些目录，不经过任何文件钩子**（因为是在子进程内、Pathwinder 注入之前的早期初始化阶段）。C: 上数据已不存在，进程启动后立即崩溃退出。

## 3. 排查过程与失败尝试

### 3.1 手动两阶段注入（失败）

曾尝试在 CreateProcessW 钩子内，对子进程做远程注入：

1. `VirtualAllocEx` + `WriteProcessMemory` 写入位置无关 thunk；
2. `CreateRemoteThread(LoadLibraryW("Hookshot.64.dll"))`；
3. 远程调用 `HookshotLibraryInitialize` / `HookshotInjectInitialize` 获取 `IHookshot*`；
4. 再 `LoadLibraryW("Pathwinder.HookModule.64.dll")` + `HookshotMain`。

**结果**：Hookshot 的初始化函数在 Chromium 进程内解引用空指针崩溃（`0x0000000000000000` 内存写入），日志显示 `hookshotIfc=NULL`。原因是 Chromium 的早期进程环境与 Hookshot 初始化逻辑不兼容。

### 3.2 NTFS Junction Point（可行但被否决）

创建 `C:\Users\...\xwechat` → D: 和 `C:\Users\...\xwechat_files` → D: 两个 junction，文件系统级重定向对所有进程透明。**实测可以打开笔记**，但用户明确要求不依赖 NTFS Junction，需要代码层面的彻底解决。

### 3.3 关键发现：Hookshot 自动注入已生效

日志证实：Hookshot.64.exe 启动器会**自动**把 Pathwinder.HookModule.64.dll 注入到所有子进程（包括 WeChatAppEx 及其 Chromium renderer/utility/GPU 后代），16 个钩子全部安装成功，C:\Users 路径全部重定向到 D:。

问题不在注入，而在**注入之前**——WeChatAppEx 早期初始化从环境变量拿到 C: 路径时，Pathwinder 还没来得及钩住文件 API。

### 3.4 最终方案：环境变量块重写

在 CreateProcessW 钩子中，重写传递给子进程的**环境变量块**：遍历所有 `NAME=VALUE` 对，对值为 `X:\...` 形态且命中重定向规则的变量，改写为 D: 路径后再传给 `Original()`。这样子进程从一开始看到的环境变量就是 D: 路径，早期初始化不再访问 C:。

## 4. 修复内容

只改动 `Source/Hooks.cpp` 一个文件，在 CreateProcessW 钩子中新增**第四层重定向**：

| 层 | v1（a2206c1） | v2（本次） |
|---|---|---|
| ① 映像路径 | ✅ `lpApplicationName` | ✅ 不变 |
| ② 命令行 | ✅ 全路径扫描重写 | ✅ 不变 |
| ③ 工作目录 | ✅ `lpCurrentDirectory` | ✅ 不变 |
| ④ 环境变量 | ❌ | ✅ **新增**：遍历环境块，重写所有命中规则的绝对路径值 |

核心逻辑（约 90 行）：

```cpp
// 遍历 NAME=VALUE\0 对，直到双 \0 结束
for (LPWSTR entry = envBlock; L'\0' != *entry;) {
    const std::wstring_view entryView(entry);
    const auto eqPos = entryView.find(L'=');
    if (eqPos != npos && eqPos > 0) {
        const std::wstring_view value = entryView.substr(eqPos + 1);
        // 仅改写 X:\... 形态的绝对路径
        if (value 看起来像盘符路径) {
            instruction = GetInstructionForFileOperation(value, ...);
            if (instruction.HasRedirectedFilename()) {
                // 改写为 D: 路径，追加到 rebuiltEnvironmentBlock
            }
        }
    }
}
// 若有任何改写，用 rebuiltEnvironmentBlock 替代 lpEnvironment
```

部署物：`payload\Pathwinder.HookModule.64.dll`（315,392 字节），通过硬链接同步到全部 18 个 runtime 目录。

## 5. 验证

- **日志证据**：WeChatAppEx 启动日志出现 `Redirecting environment variable "APPDATA" from "C:\Users\39313\AppData\Roaming" to "D:\APP\PathwinderManager\data\微信\39313\AppData\Roaming"`，`LOCALAPPDATA`/`USERPROFILE`/`TEMP`/`TMP`/`PUBLIC`/`OneDrive` 等全部重定向。
- **用户实测**：删除两个 NTFS Junction 后，从桌面快捷方式启动微信，**笔记/收藏卡片可正常打开**。
- **无崩溃转储**：WeChatAppEx 进程稳定运行。

## 6. 部署注意事项

- `D:\APP\PathwinderManager\payload\` 与 `runtime\<hash>\` 下的 DLL 通过 **NTFS 硬链接**关联，修改任一处即全局生效，无需四处拷贝。
- 不要用 PathwinderManager 部署（它会把 `LogLevel` 重置为 0 并可能覆盖 DLL）；直接替换 `payload` 目录的 DLL 即可。
